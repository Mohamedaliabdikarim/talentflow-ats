# TalentFlow ATS — Security

**Status:** Phase 0 threat model and control design. Controls are marked as Planned until implemented and tested.

## 1. Assets

- Candidate personal data (names, contact details, notes, optional CV-derived insights).
- Customer business data (jobs, pipeline state).
- Account credentials and sessions.
- Supabase service-role key, Azure OpenAI key, GitHub token (if used).

## 2. Threat model (abridged STRIDE)

## 3. Authentication and sessions

- Supabase Auth, email + password. Password policy: minimum 10 characters (configured in Supabase and mirrored in Zod).
- Sessions are HttpOnly cookies managed by `@supabase/ssr`; `proxy.ts` refreshes tokens on each request.
- Invite links are generated server-side with the admin API and shown once to the admin; they expire with the project's email OTP setting (default one hour).
- Sign-out revokes the session server-side.
- **Credential establishment is enforced (ADR-030).** Verifying an invite, magic link or recovery link creates a session but not a user-chosen password. `requireUser()` therefore routes any signed-in user whose `app_metadata.password_set` is not `true` to `/auth/set-password` before any protected route; the flag is set (service-role only, so it cannot be forged by a user) when they complete that form. The session is never revoked, only routed, so legitimate sessions and the recovery flow are preserved.

## 4. Authorization layers

1. **Proxy (optimistic):** redirects unauthenticated requests away from protected routes. Not a security boundary.
2. **Server (authoritative for actions):** `requireUser()`, `requirePlatformAdmin()`, `requireOrgAccess(slug)` run in layouts and every Server Action.
3. **Database (final):** RLS on all tables; anon has zero privileges.

Privileged operations and their guard:

| Operation                                    | Guard                                                  | Client used  |
| -------------------------------------------- | ------------------------------------------------------ | ------------ |
| Create organization                          | `requirePlatformAdmin()`                               | service role |
| Invite / create user, add membership         | `requirePlatformAdmin()`                               | service role |
| Grant platform admin                         | `requirePlatformAdmin()`                               | service role |
| Change member role, deactivate / reactivate  | `requirePlatformAdmin()` + conditional write (ADR-040) | service role |
| All job / candidate / application operations | `requireOrgAccess()` + RLS                             | user-scoped  |

## 5. Secrets and configuration

- `.env.local` for local development (git-ignored). `.env.example` documents variable names only.
- Production secrets in Vercel environment variables (ADR-043); never in the repository or build logs.
- `src/lib/env.ts` validates variables at startup with Zod and separates public (`NEXT_PUBLIC_*`) from server-only names.
- Demo credentials are shared through a private channel, never in README, commits or the video.

## 6. Privacy

- Data minimization: only fields needed for recruiting are stored.
- Synthetic data only in demos and tests.
- Retention: AI insights can be deleted per candidate; deleting a candidate cascades to applications and insights.
- Processing of real applicant CVs requires a documented lawful basis and is out of scope for the demo (see `docs/AI_FEATURE.md`).

## 7. Required security tests (see `docs/TEST_PLAN.md`)

- Cross-tenant read / insert / update / delete via RLS tests against embedded PostgreSQL.
- Non-admin cannot run provisioning actions (unit test of the guard and an E2E attempt).
- Unauthenticated access to protected pages and actions is denied.
- Service-role key is absent from client bundles (build-time grep).

## 9. Candidate CV uploads (PDF) and AI-use consent (ADR-033)

Candidate CVs are PDFs held in a **private** Supabase Storage bucket (`candidate-cvs`). Only members of the owning organization can reach a CV, and the file is never served from a public or signed URL.

**Upload validation (server-side):** `application/pdf` only, the `%PDF-` signature verified from the file bytes (a renamed non-PDF is rejected), a **4 MB** application limit (ADR-041: CVs travel through Server Actions, whose body limit is 4,400 KB in `next.config.ts`, under Vercel's 4.5 MB request cap; the `candidates_cv_size_bytes_range` check and the bucket's `file_size_limit` keep a 10 MB ceiling), the filename sanitized for display/download only, and a **server-generated, unpredictable object key** `"<organization_id>/<candidate_id>/<random-uuid>.pdf"`. Keys and logs never contain a name, email or other personal data; audit metadata carries ids only.

**Authorization (three layers):** every CV operation calls `requireOrgAccess()` (application), runs through the user-scoped client so the `candidates` RLS policy applies (database), and the `storage.objects` policies authorize on the first path segment via `can_access_org()` (storage). A user from another tenant can never read, write or delete a CV. Files are **streamed through the server** (`/o/[orgSlug]/candidates/[id]/cv`, `?download=1` for attachment); no signed or public URL is produced.

**Retention and deletion:** replacing a CV uploads the new object, repoints the row, then removes the old object. Deleting a CV clears the row metadata first (so no record points at a deleted object) and then removes the object; a rare storage failure leaves a harmless orphan rather than a broken reference. Deleting the candidate removes the row (cascade) and best-effort removes the CV object. Partial failures are explicit: if metadata cannot be written after an upload, the just-uploaded object is removed (no orphan); at creation time a storage failure rolls the candidate back so creation stays atomic.

**AI-use consent (candidate source rule):** a recruiter uploading a candidate-provided CV does **not** grant permission to analyse it with AI. `cv_source` records `candidate_provided_recruiter_upload`; `cv_ai_authorized` starts **false**. Authorization is recorded explicitly through an unchecked confirmation and a stated basis, capturing who (`cv_ai_authorized_by`), when (`cv_ai_authorized_at`) and the basis (`cv_ai_authorization_basis`); a check constraint forbids authorization without a CV. It can be **revoked** at any time, and is reset to false whenever the CV is replaced or deleted. Permission is never inferred from a LinkedIn or GitHub URL. No AI analysis is implemented in this phase; when it is added it must require `cv_ai_authorized = true`.

**Audit:** `candidate.cv_uploaded`, `candidate.cv_replaced`, `candidate.cv_deleted`, `candidate.cv_ai_authorized`, `candidate.cv_ai_revoked`, each with organization and candidate ids only — never a filename, URL or document content.

**CV detail extraction at creation (ADR-039, owner decision):** the CV stays optional. When a recruiter chooses a PDF in the "Add candidate" form, the file is validated like an upload, its text is read in memory and sent once to Azure OpenAI with the strict contract `candidate-profile-extract-v1` (seven nullable contact/profile fields, copied literally or null; no summary, skills or judgement). The validated, sanitised values (lengths, email format, LinkedIn/GitHub profile-URL rules; invalid values dropped with a warning) prefill only the fields the recruiter has not typed into; the recruiter reviews and saves. Nothing from the model is stored unless the recruiter submits it; `cv_ai_authorized` stays false; no insight is produced; the audit event `candidate.cv_details_extracted` carries counts only. This is AI processing of the CV before any AI-use authorization is recorded for that candidate: the owner decided it is automatic for data-entry assistance; the hint under the file input says so, and whether candidates must be informed is an owner decision. The preview never calls the extraction.

**Hosted setup (manual, requires the owner's approval, not done in this phase):**

1. Apply migration `supabase/migrations/20261021120000_candidate_cv.sql` through the approved `pnpm supabase:hosted push` path.
2. Apply `supabase/storage/candidate-cvs.sql` once in the hosted project (SQL editor or Management API): it creates the private bucket and the four `storage.objects` policies. Rollback statements are at the bottom of that file; the migration is reversible by dropping the added columns.

**Unverified without hosted Storage:** real upload / view / replace / delete round-trips need the hosted bucket and PostgREST, which the local harness does not provide. They are covered indirectly by the validation unit tests, the action unit tests (authorization, consent, compensation), the database tests (cross-tenant CV metadata isolation and consent constraints), an emulated `storage.objects` policy-isolation test, and the jsdom card tests; full browser E2E of the live upload remains a hosted-test item.

## 10. AI Candidate Insights (job match) — ADR-035/036/037

**What leaves the server:** only for an application whose candidate has a CV and `cv_ai_authorized = true`, the extracted CV text plus the job title/description are sent to Azure OpenAI (`gpt-5-mini`, ADR-034) as delimited data blocks. CV text exists only in memory during a run; TalentFlow stores the validated structured result (`job-match-v1`), a SHA-256 `input_hash`, versions and timestamps — never the CV text, never the prompt. The result contains no score, ranking or hiring recommendation (the schema forbids extra keys; the three assessment statuses are the only verdicts, and `not_evidenced` means "no evidence in the provided material", not "lacks").

**Authorization is checked four times:** at enqueue (user-scoped client, RLS), at claim (runner), immediately before the model call, and before persisting. Revoking authorization or deleting the CV clears every derived result (`status = revoked`, `result`/`summary` null) and makes a running analysis's completion write affect zero rows (`… WHERE status = 'analyzing'`). Deleting the candidate or the application cascades.

**Tenant isolation:** `candidate_ai_insights` carries `organization_id` with the standard `can_access_org` policy; composite FKs `(candidate_id | job_id | application_id, organization_id)` make a cross-tenant link impossible. The runner is the only service-role consumer outside provisioning: it runs behind `POST /api/insights/run`, authenticated by `INSIGHTS_RUNNER_SECRET` (constant-time compare, 404 otherwise), accepts only an optional insight id, and scopes every statement by `organization_id`. The route is exempt from the session proxy because it authenticates itself.

**Logging:** ids, outcomes, timings and sanitised error kinds (`AiError`, `InsightRunError`); unexpected errors are replaced by a generic message before persisting. Tests assert that no CV marker appears in any write or log (`tests/unit/insights-runner.test.ts`).

**Audit:** `candidate.ai_insight_requested` (by the user), `candidate.ai_insight_ready` / `candidate.ai_insight_failed` (runner, null actor, ids only), `candidate.ai_insights_invalidated` (reason + count).

**Flagged, not decided here:** Azure OpenAI's abuse-monitoring content retention (up to 30 days unless the resource is approved for no content logging) and the resource's region are not recorded in project documentation. The owner must confirm the resource's configuration and record it in this section before relying on the feature for real candidates (`docs/AI_INSIGHTS.md` §2).

**Hosted setup:** migrations `20261021130000_insights_enum.sql` and `20261021140000_insights_lifecycle.sql` were applied 2026-10-21 through the approved push path (history 7, schema fingerprint identical to local); still needed: `INSIGHTS_RUNNER_SECRET` in the server environment; a scheduled call to the runner (`docs/DEPLOYMENT.md` §4.6).

**GitHub profile evidence (ADR-038, contract `job-match-v2`):** the candidate's existing `github_url` is the only input and is parsed to one exact login; nothing is searched, guessed or auto-corrected, and an account that answers with a different login is treated as not found. A **separate, explicit authorization** (`github_ai_authorized` + who/when/basis, default false, revocable, impossible without a URL by check constraint, reset whenever the URL changes or is removed) gates its use. Only public data is read, only through the official REST API (`/users`, owner repositories without forks, languages, raw READMEs), bounded to 8 repositories, 5 README excerpts of 2,500 characters and 24,000 characters in total; no `/search` endpoint is ever called; `GITHUB_TOKEN` (optional, public-read scope) is server-only. GitHub text enters the prompt as neutralised, delimited data blocks and the instructions state that repositories show exposure, not proficiency, seniority or years; star counts and language percentages are never passed. Every evidence item is attributed to `cv` or `github`; the server rejects a GitHub attribution when no GitHub evidence was supplied and keeps only repository links from the list it gave the model. Persisted: `evidence_sources`, `github_login`, `github_status`, `github_fetched_at` and the repository URLs (`source_urls`); README text and descriptions are not stored. Any GitHub failure (invalid URL, not authorized, not found, rate limit, outage) degrades to a CV-only analysis with the reason recorded for the reviewer. Revoking GitHub authorization, or changing the URL, invalidates only GitHub-sourced insights, including runs in flight; CV revocation keeps its full effect. LinkedIn remains a manual-review link and is never analysed. Tests assert that no README marker reaches any write or log (`tests/unit/insights-runner.test.ts`).

**Flagged (owner decisions):** whether to provision a fine-grained `GITHUB_TOKEN` for the hosted environment (unauthenticated calls are limited to 60/hour per IP), and whether candidates must be informed that their public GitHub activity was analysed. Migration `20261021150000_github_evidence.sql` was applied to the hosted project 2026-10-21 through the approved push path (history 8, schema fingerprint identical to local, data hashes unchanged).

# Proposed migration 0004 — privilege hardening: review for approval

**Date:** 2026-10-20. **File:** `supabase/migrations/20261019140000_privilege_hardening.sql` (reviewed while it lived in `supabase/proposed/`; moved unchanged, sha256 `3cb873b4…`). **Status:** approved by the owner and **applied to the hosted project on 2026-10-20**, verified read-only afterwards (§9).

**Verdict in one paragraph.** The migration only removes privileges; it grants nothing new except EXECUTE on one trigger function to the Auth service role. Every statement acts on objects owned by `postgres`, the role the CLI uses, on an empty database with zero users. The complete database suite passes with the migration applied on a copy of the hosted privilege state, and a dedicated test reproduces the hosted findings before and after. It can be applied safely. Two things changed in the file since it was first committed, after measuring the hosted project more precisely: it now also revokes `MAINTAIN` (a PostgreSQL 17 privilege the hosted tables carry), and it removes Supabase's default table privileges for `service_role` as well as `anon` and `authenticated`, so future tables start with no API-role privileges, exactly as they do locally.

## 2. What it does not change

- The DML grants from migration 0002 (`SELECT, INSERT, UPDATE, DELETE` for `authenticated` and `service_role`, with the narrower sets on `platform_admins`, `audit_events`, `profiles`).
- `service_role` on existing tables: it keeps all privileges. It is server-only, bypasses RLS, and is used only behind `requirePlatformAdmin()`.
- The RLS helper functions and RPCs (`is_platform_admin`, `is_org_member`, `can_access_org`, `shares_organization_with`, `log_audit_event`, `activate_my_memberships`): still executable by `authenticated`, still denied to `anon`.
- The three `SECURITY INVOKER` trigger functions (`set_updated_at`, `prevent_organization_change`, `touch_stage_changed_at`), all policies, tables, columns, indexes, triggers: untouched. The schema fingerprint does not hash grants, so it stays `227fed80180eced8183d19d5634a8ee0` after the migration.
- Generated types: `pnpm db:types` produces no diff (privileges are not part of the types).

## 6. Can it be applied safely to the empty hosted database?

Yes.

- Every statement is a `REVOKE`, an `ALTER DEFAULT PRIVILEGES … REVOKE`, or one `GRANT EXECUTE` to the Auth role. No table, column, policy, index or row is touched; no data exists.
- The CLI applies a migration file inside a single transaction, so a failure leaves the database as it was. Catalog updates take only brief locks, and the database is idle.
- It is reversible: a compensating migration can `GRANT` the privileges back; nothing is dropped.
- PostgREST needs no schema reload for privilege changes.
- Local evidence covers both the isolated before/after check and the entire suite on the hosted-like state.

**Apply path once approved (each step reported, stop on anything unexpected):** move the file unchanged into `supabase/migrations/`; `pnpm db:verify`; `pnpm db:types` (expect no diff); `pnpm supabase:hosted dry-run` (expect exactly `20261019140000_privilege_hardening.sql`); `pnpm supabase:hosted push`; then read-only: `migration list` (4 versions), the table/function privilege queries (expect `authenticated` = DML only, `anon` none, trigger function limited to owner and `supabase_auth_admin`), `pg_default_acl` (no API-role entry on tables), `get_advisors` (the two trigger-function WARNs gone), schema fingerprint unchanged.

## 7. Remaining risks and trade-offs

- **Future migrations must grant explicitly.** After statement 2 a new table on the hosted project gives the API roles nothing by default, the same as locally. Every migration that creates a table must `grant select, insert, update, delete on <table> to authenticated, service_role` (as 0002 does) in addition to its policies. A forgotten grant fails the local suite the same way it would fail on hosted, which is the point. `CLAUDE.md` rule 5 now says so.
- **Supabase may re-create `rls_auto_enable()`** on a platform upgrade with PUBLIC execute restored. Harmless (the function only enables RLS on new tables); the advisor would warn again. If you prefer not to touch a platform-managed object, statement 4 can be dropped from the file without affecting anything else.
- **Advisor warnings that remain by design:** the six `SECURITY DEFINER` helpers and RPCs executable by `authenticated`. They are the app's authorization helpers; each reads only data scoped to `auth.uid()` or writes an audit row with the caller as actor, and `anon` is denied.
- **`service_role` keeps `TRUNCATE`, `REFERENCES`, `TRIGGER`, `MAINTAIN` on existing tables.** It bypasses RLS anyway and is never exposed to a browser; revoking is possible but was left out to keep the admin client's rights unchanged.
- **Not included (optional):** a global `ALTER DEFAULT PRIVILEGES REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC` would make every future function non-callable by default. The current convention (each migration revokes from PUBLIC and grants per function, as 0002 and 0003 do) achieves the same per function; the global form also affects schemas other than `public`, so it is left to a separate decision.
- **`MAINTAIN` requires PostgreSQL 17.** If the project were ever restored onto PostgreSQL 16, statement 1 would fail; the hosted project runs 17.11.
- **Unchanged by this migration:** the `auth.users` → `profiles` trigger has still never fired on the hosted project; the first `pnpm bootstrap:admin` (separate approval) is its first real run and will be checked by reading `profiles`.

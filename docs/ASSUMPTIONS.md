# TalentFlow ATS — Assumptions

Each assumption was necessary to make progress without blocking on the project owner. Confirmed assumptions become decisions in `docs/DECISIONS.md`; rejected ones are updated here with the date.

| #   | Assumption                                                                                                                                                                                         | Why it was necessary                                                                 | Status                                      |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------- |
| A1  | Each customer organization is one tenant; a user may belong to several organizations, but typically belongs to one.                                                                                | Platform admins manage many customers; the schema must isolate them.                 | Proposed                                    |
| A2  | Two roles are enough for v1: `platform_admin` (vendor) and organization member (`owner` or `member`, identical permissions in v1).                                                                 | Keeps authorization simple; roles are stored in tables, not client claims.           | Proposed                                    |
| A3  | Candidate and application are separate records; the Kanban shows applications.                                                                                                                     | Enables one person on several jobs without duplicates.                               | Proposed (ADR-004)                          |
| A4  | Pipeline stages are fixed: New, Screening, Interview, Offer, Hired, Rejected. Rejected is shown as a column that can be collapsed.                                                                 | Custom stages are out of scope for seven days.                                       | Proposed                                    |
| A5  | Onboarding uses invite links generated by the admin and shared out of band; email delivery is optional.                                                                                            | Supabase's default mailer only delivers to project team members without custom SMTP. | Proposed (ADR-007)                          |
| A6  | LinkedIn is a stored URL only. No scraping or automated access.                                                                                                                                    | LinkedIn terms and the absence of a general-purpose API.                             | Proposed (ADR-013)                          |
| A7  | GitHub enrichment, if built, uses the official public REST API and cites repository URLs.                                                                                                          | Evidence-based and permitted.                                                        | Proposed                                    |
| A8  | AI insights are advisory, require human review, and are built only after the core passes its tests.                                                                                                | Protects the core delivery; aligns with the spec's delivery gate.                    | Proposed                                    |
| A9  | Demo data is synthetic.                                                                                                                                                                            | Privacy.                                                                             | Proposed                                    |
| A10 | Hosting is Azure App Service (Linux, Node 22) with the Next.js standalone output; Supabase is hosted (free or pro tier chosen by the owner).                                                       | Spec mandates Azure + Supabase; App Service supports a full Node server.             | Proposed; provisioning needs owner approval |
| A11 | The project lives in `C:\Users\moi-a\Desktop\talentflow-ats`, next to the owner's other projects, and will be pushed to a private GitHub repository under the owner's account only after approval. | Spec forbids publishing without approval.                                            | Proposed                                    |
| A12 | Cache Components are disabled; all tenant pages render dynamically.                                                                                                                                | Avoids cross-user caching risk and Next.js 16 migration work.                        | Proposed (ADR-003)                          |
| A13 | Login is email + password only (no OAuth/SSO) for v1.                                                                                                                                              | Reduces configuration and demo risk.                                                 | Proposed                                    |
| A14 | A platform admin acting inside a customer workspace uses their own identity (no impersonation) and the action is audited.                                                                          | Accountability.                                                                      | Proposed (ADR-006)                          |
